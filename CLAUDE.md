Skills are data first (`Skills/*.tres` built from existing `Skill.gd` fields and `Effect` stats); anything new a skill does goes in a `Behaviours/*.gd` script with `apply()` and `describe()` side by side. A new `Skill.gd` field is allowed only when it removes duplication or enables a shared system (the user, 2026-11-19: "restrict creep but not anything that alleviates DRY and builds rich systems"); each one is listed as a question for the user to confirm, and `FLAG_CEILING` is a creep alarm the tool raises with a note (`python3 Util/skill.py ceiling "<field: why>"`), not a ban.
Add one with `python3 Util/skill.py new` (writes the .tres, wires it onto a tree/role, stubs its behaviour and `Tests/<id>_test.gd`; see `.claude/skills/new-skill`), not by hand-editing .tres ids, and run `python3 Util/skill.py check` before committing.
`Battle.gd`, `HUD.gd` and `Unit.gd` run to thousands of lines: grep and read ranges, never whole files.
Tests: `godot --headless --path . --import` after adding a script or class_name, then `godot --headless --path . -s Tests/run.gd -- [words]` (words match `file.test_name`; none runs all, ~60 s, ending `N checks, M failed`; `quick` skips `Tests/slow.txt`, `reverse` runs files backwards to catch order leaks, `soak` runs all 30 combat seeds; a test that hits a script error counts as failed); a compile error hangs it. **Lean tests:** a data-only skill gets no test file (`Tests/sweep_test.gd` casts or applies every one); only a skill with a new `Behaviours/*.gd` gets its own, and a skill that is a basic tagged attack, heal or buff, or just recombines existing effects and mechanics, is tested through the core mechanic it uses, not a copy per skill. `skill.py new` stubs a test only for a new behaviour; `unit.py` and `mechanic.py` stub one only with `--test`. One test per rule; prove one earns its place by breaking the rule and watching it fail.
**Every name an AI makes up gets ` ??` after it** - skills (`ai = true`, shown "Name ??"), tiles, classes, trees, units, factions, tags, properties, effects - until a person reviews it; a name the user gave goes in as it is (the tools' `--human`), and so does a word taken from the user's own words (a tag or stat they described: no `??`). A `??` is for a genuinely AI-invented tag and goes on its shown name only, never on its id or in a way that breaks a lookup (`has_tag`, parents, Glossary links); `mechanic.py check` fails an id with one. Skill names are unique (shown names too, `??` aside; `skill.py check`). Note each such call in the todo docs, annotated with the choice made.
New content goes through its tool and its process in `.claude/skills/`: `new-skill` (`Util/skill.py`), `new-tile` (`Util/tile.py`), `new-class` (`Util/role.py`), `new-unit` (`Util/unit.py`, factions too), `new-item` (`Util/item.py`, loot tables too), `new-mechanic` (`Util/mechanic.py`: tags, properties, statuses, Effect stats). Unit sprite poses (`-left`, `-right`, `-neutral`, numbered) become per-state animations (`Units/<Name>.tres`) through `Util/anim.py setup`. Each tool has `check`; run the ones you touched, and `skill.py check`, before committing.
Art is a placeholder PNG at a fixed path until real art replaces the file: `Icons/Skills/<skill>.png`, `Tiles/<terrain>.png`, `Units/<Name>.png` (`Util/icon.py` draws them).
Keep Unit, Battle and the HUD loosely coupled: a unit emits a signal (with a mutable payload where listeners may change the outcome: `Unit.taking_hit`), Battle listens and dispatches to behaviours; don't hand a Unit a Battle reference or make one system reach into another's state to add a feature.
**Composability (`docs/plan-composability.md`):** prefer shared tags and one generic hook over bespoke counters or one-off flags (no "hoagie token only hoagie skills use"); unintended interactions beat sandboxed, tightly coupled systems; but don't over-abstract.
**Delegating (`.claude/skills/coordinate`):** for multi-part work the session is a host: it splits the request (or `docs/queue.md`) into builder tasks on cheaper models, each in its own worktree, then merges, verifies, pushes and has a docs keeper record the calls as numbered questions.
**Naming:** stubbing and naming use the preferred terms in `docs/g-dictionary.md` ("Arcalís" for arcane/magic broadly); lore lives in `docs/g-glossary.md`.
