Skills are data first (`Skills/*.tres` built from existing `Skill.gd` fields and `Effect` stats); anything new a skill does goes in a `Behaviours/*.gd` script with `apply()` and `describe()` side by side, never a new `Skill.gd` flag.
Add one with `python3 Util/skill.py new` (writes the .tres, wires it onto a tree/role, stubs its behaviour and `Tests/<id>_test.gd`; see `.claude/skills/new-skill`), not by hand-editing .tres ids, and run `python3 Util/skill.py check` before committing.
`Battle.gd`, `HUD.gd` and `Unit.gd` run to thousands of lines: grep and read ranges, never whole files.
Tests: `godot --headless --path . --import` after adding a script or class_name, then `godot --headless --path . -s Tests/run.gd -- [words]` (words match `file.test_name`; none runs all, ~30 s, ending `N checks, M failed`); a compile error hangs it.
**Every name an AI makes up gets ` ??` after it** - skills (`ai = true`, shown "Name ??"), tiles, classes, trees, units, factions, tags, properties, effects - until a person reviews it; a name the user gave goes in as it is (the tools' `--human`). Note each such call in the todo docs, annotated with the choice made.
New content goes through its tool and its process in `.claude/skills/`: `new-skill` (`Util/skill.py`), `new-tile` (`Util/tile.py`), `new-class` (`Util/role.py`), `new-unit` (`Util/unit.py`, factions too), `new-mechanic` (`Util/mechanic.py`: tags, properties, statuses, Effect stats). Each tool has `check`; run the ones you touched, and `skill.py check`, before committing.
Art is a placeholder PNG at a fixed path until real art replaces the file: `Icons/Skills/<skill>.png`, `Tiles/<terrain>.png`, `Units/<Name>.png` (`Util/icon.py` draws them).
Keep Unit, Battle and the HUD loosely coupled: a unit emits a signal (with a mutable payload where listeners may change the outcome: `Unit.taking_hit`), Battle listens and dispatches to behaviours; don't hand a Unit a Battle reference or make one system reach into another's state to add a feature.
